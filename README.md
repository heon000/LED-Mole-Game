# 라즈베리 파이를 활용한 LED 두더지 게임 (IoT Mole Game)

3학년 2학기 'IoT 실습과 응용' 강의에서 배운 임베디드 GPIO 제어, 실시간 비동기 프로그래밍 및 TCP/IP 네트워크 통신 기술을 종합하여 구현한 IoT 기반 대전형 LED 두더지 게임 프로젝트입니다.

> 본 프로젝트는 2025년도 3학년 2학기 과제물로, 취업 포트폴리오 관리를 위해 로컬 컴퓨터에 보관 중이던 소스코드를 깃허브 레포지토리로 이관한 프로젝트입니다.

---

## 1. 프로젝트 소개
* **진행 기간**: 2025.11 ~ 2025.12 (약 2개월)
* **개발 배경 및 목적**:
  * 단순한 단편적 GPIO 실습을 넘어 LED, 키패드, Text LCD, 부저 등 다수의 주변 장치를 단일 프로세스에서 지연 없이 제어하는 실시간 임베디드 제어 기법을 확립합니다.
  * `delay()` 블로킹 방식의 한계를 극복하고 `millis()` 기반 비동기 시분할 스케줄링을 적용하여 실시간 입출력을 처리합니다.
  * C언어(하드웨어 제어/로직)와 Python(TCP 서버/Firebase DB 연동)을 결합한 하이브리드 아키텍처를 구축하고, TCP/IP 소켓 통신을 통해 여러 대의 독립된 라즈베리 파이 간 실시간 멀티 네트워크 대전을 구현합니다.

## 2. 기술 스택
* **개발 언어**: C, Python
* **운영체제 환경**: Raspberry Pi OS (Linux), Window 10 / 11
* **개발 도구(IDE):** GCC (Linux CLI), Visual Studio Code
* **서버 및 네트워크:** TCP/IP Socket (Non-blocking I/O), Windows Multi-threaded Server
* **데이터베이스:** Google Firebase Realtime Database
* **하드웨어 환경:** Raspberry Pi, 8-Switch, 8-LED, Text LCD (16x2), Buzzer

  * Python (Server): `socket`, `threading`, `time`, `random`

## 3. 시작 가이드 및 실행 방법

### 📌 하드웨어 연결 (WiringPi GPIO Pin Map)
* **LED (8개)**: GPIO 5, 6, 13, 19, 26, 12, 16, 20
* **Keypad (8개)**: GPIO 2, 3, 4, 17, 27, 22, 10, 9
  * *메뉴 조작 키 매핑*: 0번(UP), 1번(DOWN), 2번(ENTER), 3번(BACK)
* **Text LCD (16x2)**: RS(18), E(23), D4(8), D5(7), D6(24), D7(25)
* **Buzzer**: GPIO 21

### 📌 실행 방법

#### 1) 중앙 중계 서버 실행 (Server PC)
```bash
# 별도 Windows PC에서 server.py 실행 (기본 포트 9000 오픈)
python server.py
```

#### 2) 라즈베리 파이 클라이언트 컴파일 및 실행 (각 기기 1P, 2P)
```bash
# C 소스코드 내 SERVER_IP를 서버 PC의 IP 주소로 수정 후 빌드
gcc -o mole_game IoT.c -lwiringPi -lwiringPiDev -lpthread

# 루트 권한으로 실행
sudo ./mole_game
```

#### 3) 게임 조작 방법
* **메인 메뉴:** LCD 화면에 표시되는 `Single Play`, `Multi Play`, `Ranking`, `Exit` 메뉴를 키패드 0~3번 버튼으로 탐색 및 선택합니다.
* **Single Play:** 30초 동안 혼자서 게임을 진행하며 난이도 상승(Lv1~3), 콤보 점수, 시간차(엇박자) 스폰을 공략합니다. 게임 종료 후 콘솔에 영어 이니셜(3자리)을 입력하면 Firebase DB로 점수가 업로드됩니다.
* **Multi Play:** 각 라즈베리 파이에서 `Multi Play` 메뉴 진입 후 `KEY_ENTER(2번 버튼)`를 눌러 레디 상태로 전환합니다. 모든 플레이어가 레디하면 3초 카운트다운 후 실시간 대전이 시작되며, LCD에 내 점수와 실시간 1등(라이벌) 점수가 동기화됩니다.
* **Ranking:** 메인 메뉴에서 `Ranking` 선택 시 Firebase DB에 저장된 상위 1~10위 랭킹을 터미널 콘솔로 조회합니다.

### 📂 주요 모듈별 상세 역할
* `IoT.c` (라즈베리 파이 메인 제어):
  * `KeypadReadState()`: 8개 입력 핀 상태를 비트 연산(`state |= (1 << i)`)으로 8비트 정수로 패킹.
  * `waitForKeyPressMenu()`: 메뉴 탐색 시 엣지 검출을 통해 단일 클릭 이벤트만 반환.
  * `playToneNB()` / `checkSound()`: 타임스탬프를 활용해 딜레이 없이 소리를 자동 차단하는 부저 제어.
  * `playSingleGame()`: 자체 난수 생성, 레벨별 생존시간 단축, 콤보 가산점 로직이 포함된 싱글 루프.
  * `playMultiGame()`: 논블로킹 수신 버퍼 스트림(`\n` 파싱) 처리 및 실시간 `HIT` 전송 루프.
  * `sendScoreToFirebase()` / `showRanking()`: 파이썬 스크립트 실행을 통한 DB 업로드 및 랭킹 조회.
* `server.py` (중앙 중계 서버):
  * `accept_clients()` / `wait_for_start_signal()`: 멀티플레이어 접속 수락 및 전원 레디 동기화.
  * `handle_client()`: 플레이어별 입력 이벤트(`HIT`) 처리, 오답 감점(-10점), 레벨 상승(150점/300점), 5콤보 보너스(+5점) 연산.
  * `start_game_logic()`: 30초 타이머 제어, 레벨별 엇박자 두더지 생성 및 타임아웃 감점 처리.

## 7. 트러블 슈팅 및 문제 해결 과정

### 1. 단일 키트 자원 분할(Local Split)의 한계와 소켓 기반 네트워크 멀티플레이로의 아키텍처 전면 개편
* **문제점:** 초기 설계에서는 단일 라즈베리 파이 보드(8개 버튼/LED)를 4개씩 나누어 두 명이 플레이하는 로컬 분할 방식을 계획했습니다. 그러나 실제 테스트 결과 좁은 보드 위에서 두 명의 손이 겹치며 심각한 물리적 간섭이 발생했고, 4개 버튼만으로는 게임 난이도와 재미가 반감되는 UX 문제가 드러났습니다. 또한 이는 단순 임베디드 제어에 불과하여 'IoT 실습'이라는 교과목 취지에 부합하지 못했습니다.
* **해결방안:** 2대의 독립된 라즈베리 파이 키트를 활용하고, 중앙에 Python TCP/IP 소켓 서버를 도입하여 각 플레이어가 온전한 8개 버튼을 사용하는 원격 네트워크 대전 방식으로 설계를 전면 전환했습니다. 서버-클라이언트 간 경량 문자열 프로토콜(`START`, `LED [N]`, `HIT [N]`, `SCORE [A] [B]`, `GAMEOVER`)을 정의하여 1ms 단위의 정밀한 실시간 동기화를 달성했습니다.

### 2. 단일 스레드 환경에서 `delay()` 블로킹으로 인한 입력 씹힘 및 `millis()` 논블로킹 타이머 도입
* **문제점:** 임베디드 리눅스 환경에서 `delay()` 함수로 게임 타이밍을 제어하자, 두더지 점등 시간 동안 CPU가 대기 상태에 갇혀 사용자의 버튼 입력이 씹히거나 소켓 패킷 수신이 지연되는 현상이 발생했습니다.
* **해결방안:** 모든 시간 제어 로직을 `delay()`(블로킹)에서 `millis()` 타임스탬프 기반의 비동기 시분할 방식으로 전면 교체했습니다. 메인 루프가 멈춤 없이 고속 회전하며 키 입력 폴링, 부저 사운드 체크, LCD 갱신 주기를 독립적으로 스케줄링하여 반응 속도를 극대화했습니다.

### 3. 랭킹 등록 진입 시 부저음(Buzzer) 지속 발생 에러 (Blocking I/O 충돌)
* **문제점:** 게임 종료 후 닉네임을 콘솔로 입력받는 단계(`scanf`, `system()`)로 진입했을 때, 직전에 울리던 종료 효과음이 꺼지지 않고 계속 울리는 하드웨어 결함이 발생했습니다. 분석 결과, `checkSound()` 폴링 함수가 루프 정지로 인해 실행되지 못해 부저 GPIO 핀이 High 상태로 고정되었기 때문이었습니다.
* **해결방안:** 블로킹 입력 함수를 호출하기 직전에 부저 PWM 출력을 강제로 0으로 초기화하는 `stopTone()` 함수를 명시적으로 호출하여 하드웨어 사운드 신호를 사전에 차단함으로써 문제를 완벽히 해결했습니다.

### 4. Text LCD 화면 갱신 시 첫 글자('S') 깜빡임 현상
* **문제점:** 빠른 게임 루프 안에서 커서 이동(`lcdPosition`)과 데이터 쓰기(`lcdPrintf`)가 빈번하게 반복되면서 "SCORE" 문자열의 첫 글자인 'S'가 주기적으로 깜빡이는 시각적 아티팩트가 발생했습니다.
* **해결방안:** LCD 컨트롤러의 첫 번째 메모리 주소 부하를 방지하기 위해 출력 시작 좌표를 `(0, 1)`에서 `(1, 1)`로 한 칸 이동시켜 문자열 시작 위치에 여백을 둠으로써 깜빡임 없는 선명한 디스플레이를 구현했습니다.

## 8. 프로젝트를 통해 배운 점 및 개선점
* **동기(Blocking)와 비동기(Non-blocking) 설계의 중요성:** 하드웨어 I/O와 네트워크 통신이 맞물린 임베디드 시스템에서는 사소한 블로킹 함수 하나가 시스템 전체의 실시간성을 붕괴시킬 수 있음을 배웠으며, 논블로킹 타이머 및 소켓 프로그래밍을 체득했습니다.
* **이종 언어 융합형 시스템 통합 역량:** 하드웨어 고속 I/O 제어에 최적화된 C언어와 네트워크/DB 통신에 유연한 Python의 장점을 결합하여 상호 보완적인 하이브리드 아키텍처를 성공적으로 구축했습니다.
* **개선점:**
  * **바이너리 패킷 직렬화 미적용:** 현재는 프로토콜이 문자열 기반(`LED 1\n`)으로 구현되어 직관적이나, 고속 네트워크 환경에서는 구조체(Struct) 메모리 블록을 직접 바이너리로 직렬화/역직렬화하여 전송하는 방식이 패킷 오버헤드를 더욱 줄일 수 있을 것입니다.
  * **하드웨어 디바운싱(RC 필터) 보강:** 소프트웨어 폴링과 엣지 검출 알고리즘으로 채터링을 효과적으로 억제했으나, 향후 하드웨어 레벨에서 슈미트 트리거 및 RC 필터를 보강한다면 CPU 자원을 더욱 절약할 수 있을 것입니다.
